# Архітектурні рішення

Цей розділ визначає, як фіксувати нові рішення, що змінюють сталі межі backend. Станом на 2026-10-15 чинних ADR у цьому каталозі немає. В [`docs/legacy/adr/`](../../../legacy/README.md) зберігаються історичні ADR; їхні номери, стек і формулювання не підтверджують поточну реалізацію без звірки з кодом та чинними документами.

Новий ADR потрібен для рішення з довготривалими наслідками: межі модулів, схема розгортання, модель даних, суттєва зміна інтеграційного чи безпекового підходу. Рішення тільки для однієї фічі спершу описуй у її `design/` під [`specs/`](../../specs/README.md). Не створюй ADR заради кожного пакета або локального рефакторингу.

Для нового ADR збережи окремий файл з унікальним номером і короткою назвою. Укажи дату, статус (`пропозиція`, `прийнято`, `замінено`), контекст і джерела фактів, розглянуті варіанти, обране рішення, наслідки та посилання на пов'язані специфікації. Коли рішення зміниться, не стирай історію: додай новий ADR і познач попередній як замінений. Після прийняття онови відповідні оглядові документи [архітектури](../README.md) і, якщо потрібно, [стандарти](../../standards/README.md).
