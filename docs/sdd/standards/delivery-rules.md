# Правила delivery

## Порядок SDD

1. Визнач мету, обсяг, бізнес-правила й приймальні сценарії зі сталими ID `R-*` та `SC-*`.
2. З'ясуй неоднозначні приклади, потім узгодь дизайн, модель даних, ризики й контракти лише там, де для них є зміст.
3. Пов'яжи кожен сценарій із технічними завданнями та рівнем тестування в матриці traceability. Позначай завдання реалізації `TS-*`, а спільні технічні передумови — `EN-*`.
4. Виконуй готові завдання сценарій за сценарієм. Для кожного тестованого технічного зрізу застосовуй Red -> Green -> Refactor.
5. Перевір кожен завершений сценарій, потім запусти відповідну регресію.
6. Онови специфікацію свідченнями, відхиленнями та залишковими ризиками.
7. Після реалізації нової фічі додай опис поточної будови до [карти фіч](../features/README.md) і її індексу; при зміні наявної фічі звір та за потреби онови опис у тій самій зміні.

## Детальність документації

- Одна SDD-специфікація фічі має один координаційний `README.md`; короткий опис фактичної реалізації зберігається окремо в `features/`.
- Один документ відповідає за одну роль; не створюй порожніх або дубльованих файлів.
- Приймальні сценарії описують зовнішньо спостережувану поведінку без деталей реалізації.
- Дизайн-документи залишаються джерелом технічних меж і рішень.
- `traceability.md` пов'язує сценарії, технічні завдання й свідчення без дублювання їхнього змісту.
- ADR потрібен лише для тривалої архітектурної зміни; звичайні рішення сценарію використання належать до дизайну фічі.
- Специфікації фіч посилаються на `standards/`, а не копіюють сталі правила backend, API, безпеки чи тестування.

## Критерії завершення

Кожен сценарій у погодженому обсязі реалізовано або явно відкладено; його обов'язкові технічні завдання завершено, а автоматична чи задокументована ручна перевірка пройшла. Контракти відповідають реалізації. Відповідні restore/build/test перевірки виконано або записано причину їх відсутності. Звіт delivery містить змінені файли, свідчення перевірки, неперевірену роботу й залишкові ризики.
