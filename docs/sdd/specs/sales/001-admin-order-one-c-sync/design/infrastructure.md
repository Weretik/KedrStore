# Замовлення адміністратора та синхронізація з 1C — дизайн: Infrastructure

## Зберігання даних та інтеграції

`Sales.Infrastructure` відображає `Order`, `OrderLine` і `OneCOrderSync` через EF Core у `SalesDbContext`. Він надає потрібні Application абстракції репозиторіїв/запитів і межу транзакції, яка атомарно зберігає замовлення з початковим записом передавання `Pending`.

Для захоплення записів, термін яких настав, `OneCOrderSync` використовує токен оптимістичної конкурентності PostgreSQL `xmin`. Обробник змінює стан такого запису на `Sent` і зберігає його до SOAP-виклику; `DbUpdateConcurrencyException` означає, що запис захопив інший обробник, тому поточний його пропускає. Захоплення використовує механізм провайдера й запобігає одночасним SOAP-надсиланням для одного запису передавання.

Новий адаптер запису Sales обгортає `OneCSoapClientFactory` і згенеровану операцію `CreateSiteRequestAsync(RequestData)`. На межі Infrastructure адаптер відображає DTO передавання, яким володіє Application, на згенеровані типи WCF; `Generated/Reference.cs` не змінюється. Він інтерпретує узгоджені форми відповіді про прийняття й бізнес-помилку, перетворює транспортні винятки та ніколи не записує в журнал облікові дані чи необроблені чутливі дані запитів.

`SyncOneCOrdersJob` реєструється в Sales Infrastructure і викликається наявним host `Host.Jobs`, який виконує один запуск. Завдання безпечно захоплює записи, термін яких настав, зокрема завислі спроби `Sent`, дотримується київського вікна передавання, надсилає налаштований пакет із паузами, фіксує результати й застосовує графік повторів. `OneCOrderSyncOptions` належить Sales Infrastructure, перевіряється ним і прив'язується до секції `Sales:OneCOrderSync`; він керує розміром пакета, затримкою між викликами, максимальною кількістю спроб, межами вікна надсилання й затримкою відновлення завислого `Sent`. Під час відновлення повторно використовується незмінний `OrderNumber`, який OneC обробляє без ризику дублювання. Структуровані журнали містять `OrderId`, `AttemptCount`, `Status` і контекст кореляції; метрики охоплюють прийняті замовлення, транспортні/бізнес-помилки, чергу повторів і чергу невдалих доставок.

Коли передавання переходить у `DeadLetter`, адаптер Telegram у Sales Infrastructure надсилає одне сповіщення про помилку. Спроби сповіщення надійно зберігаються в `OneCOrderSync`, захоплюються через PostgreSQL `xmin` і повторюються за графіком `5m -> 15m -> 30m -> 1h -> 3h`, щонайбільше п'ять разів. Після вичерпання спроб помилка залишається видимою, а стан `DeadLetter` не змінюється. Успішне сповіщення встановлює `DeadLetterNotifiedAtUtc` і запобігає повторному надсиланню. Повідомлення містить клієнта, замовлення й остаточну очищену помилку; до нього додається файл Excel зі збереженими знімками рядків. Сервіс сповіщень та експортер Excel використовують абстракції Sales Application і не повинні прив'язувати Sales до типів запитів публічних швидких замовлень Catalog.

Ручний повтор — команда Application, яку підтримує `IOrderSyncRetryStore`. Її адаптер Infrastructure завантажує замовлення й запис синхронізації, перевіряє кінцевий стан, додає `OrderSyncRetryAudit` і переводить агрегат у `RetryScheduled` в одній транзакції `SaveChanges`. Агрегат скидає стан спроб і сповіщень поточного циклу, тоді як аудит зберігає попередню помилку. API повертає відповідь після збереження, а наявне завдання передавання пізніше виконує SOAP-виклик. Той самий токен `xmin` відхиляє одночасні переходи повтору.

## Міграція та розгортання

Для цієї фічі потрібна нова міграція EF Core для бази даних Sales. Її слід згенерувати через передбачений у репозиторії шлях EF CLI, перевірити індекси й руйнівні операції та застосувати до порожньої тестової бази, сумісної з PostgreSQL, перед випуском.

Порядок розгортання: застосувати схему перед увімкненням запланованого надсилання; розгорнути API й код завдання; потім увімкнути планувальник лише в межах налаштованого київського вікна. Відкат передбачає відкат застосунку й вимкнення завдання; нові таблиці замовлень і передавання зберігаються, щоб не втратити бізнес-записи в очікуванні. Після можливого створення замовлень схема автоматично не відкочується.

Наявний `SALES_1C_SYNC_INSTRUCTION.txt` є операційним джерелом цієї фічі для повторних спроб, обмеження частоти, планування, ідемпотентності та діагностики. Конфігурація Cloud Scheduler на рівні розгортання залишається поза межами цього репозиторію.
