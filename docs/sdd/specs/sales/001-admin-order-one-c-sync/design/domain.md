# Admin order and 1C synchronization — design: Domain

## Responsibility

`Sales.Domain` gains an `Order` aggregate with encapsulated order lines and a required `CounterpartyId`. The aggregate owns input-independent order invariants: a non-empty line collection, positive quantities, valid product identifiers, and immutable identity/counterparty binding after creation.

`OneCOrderSync` is a separate Sales aggregate root, linked one-to-one to `Order` by the typed `OrderId` value object (backed by database `bigint`). It owns only delivery-state transitions: attempt count, scheduled time, terminal states, sanitized diagnostics, and acceptance metadata. Its record is created atomically with the order and safely claimed by the background job.

The Domain has no SOAP, HTTP, EF Core, scheduler, or Cloud Run dependency. No domain event is required for the initial flow: the durable `Pending` record is the hand-off to the scheduled job.

## Intermodule interaction

- `CounterpartyId` is the imported 1C string identifier owned by Sales. The creation use case checks its local existence through a Sales abstraction; it does not request customer data from 1C.
- Product IDs are persisted as the external identifiers supplied by the admin frontend. The create command validates their non-empty form; 1C remains the authoritative business validator for product availability and rejects unknown identifiers as a business error.
- `Order.Id` is `OrderId`, a type-safe Domain value object backed by technical database `long`. `Order.OrderNumber` is an immutable human-readable number (`SO-YYYYMMDD-NNNN`) generated by Sales and sent to 1C as the external key.

## Risks

- Concurrent workers must not claim and submit the same pending delivery record simultaneously.
- A process failure after 1C receives a request but before Sales records acceptance is possible; stable `OrderId` and 1C deduplication are mandatory.
- Monetary values use the agreed line-total semantics and must retain their exact decimal value through the SOAP mapping.
