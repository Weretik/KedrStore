# Замовлення адміністратора та синхронізація з 1C — контракт HTTP і SOAP

**Статус:** узгоджені базові рішення

## Споживачі та сумісність

Споживачем є адміністративний frontend, яким користуються менеджери з продажів. Це новий API; він не змінює анонімний endpoint швидкого замовлення Catalog `POST /api/orders`. За явним рішенням endpoint тимчасово анонімний; перед використанням у продукційному середовищі потрібна авторизація Manager/Admin.

## HTTP-операція

`POST /api/admin/orders`

Структура запиту:

```json
{
  "counterpartyId": "000000000",
  "comment": "optional manager comment",
  "lines": [
    {
      "productId": "000000000",
      "quantity": 2,
      "amount": 12500.00
    }
  ]
}
```

Структура успішної відповіді:

```json
{
  "orderId": 12345,
  "orderNumber": "SO-20260817-0001",
  "syncStatus": "Pending"
}
```

`orderId` — локальний `OrderId` (`bigint`), призначений базою даних. `orderNumber` — незмінний читабельний номер і зовнішній ідентифікатор для 1C у форматі `SO-YYYYMMDD-NNNN`. Окремий публічний UUID не потрібен.

Endpoint тимчасово має атрибут `[AllowAnonymous]`. Наступний крок для продукційного середовища — замінити його на `[Authorize(Policy = PolicyNames.CanManageOrders)]`; наявна політика дозволяє ролі Manager і Admin. Для запиту потрібен заголовок `Idempotency-Key`: непрозорий UUID, який frontend генерує один раз для кожної дії створення. Backend атомарно із замовленням зберігає ключ, канонічний хеш запиту й початковий результат замовлення. Ідентична повторна спроба повертає `200 OK` із початковим результатом; повторне використання ключа з іншими даними запиту повертає `409 Conflict`. Ключі зберігаються 24 години, після чого безпечно видаляються без видалення замовлень. Очікувані помилки: `400` за помилки валідації, `404` для невідомого/видаленого контрагента та `409` за конфлікту ідемпотентності. Після ввімкнення авторизації додати `401` і `403`. Внутрішні помилки SOAP ніколи не повертаються як необроблені подробиці.

Після узгодження створити `docs/sdd/contracts/sales/admin-order-one-c-sync.openapi.yaml` і додати його `$ref` до `docs/sdd/contracts/openapi.yaml`.

## Контракт статусу синхронізації замовлення адміністратора

`GET /api/admin/orders/{orderId}/sync-status` повертає стан передавання одного замовлення. Він тимчасово має `[AllowAnonymous]`; перед використанням у продукційному середовищі його слід захистити через `PolicyNames.CanManageOrders` (Manager і Admin). Відповідь містить лише `orderId`, `orderNumber`, `syncStatus`, значення `oneCDocumentNumber`, яке може бути null, і значення `acceptedAtUtc`, яке може бути null. `oneCDocumentNumber` відображається з `OneCOrderSync.OneCDocumentNumber`; frontend показує його лише після прийняття замовлення в 1C. Внутрішні діагностичні дані SOAP ніколи не повертаються.

Версійний контракт OpenAPI визначає маршрут, тимчасовий анонімний доступ і відповіді `200`, `401`, `403` та `404`.

## Контракт ручного повтору

`POST /api/admin/orders/{orderId}/sync/retry` приймає `{ "reason": "..." }` і планує новий фоновий цикл передавання. Він ніколи не викликає 1C всередині HTTP-запиту. Лише `BusinessError` і `DeadLetter` можуть перейти в `RetryScheduled`; для невідомого замовлення повертається `404`, для некоректної причини — `400`, а для будь-якого іншого поточного стану — `409`. Успішний запит повертає `202` з `orderId`, незмінним `orderNumber` і `syncStatus: "RetryScheduled"`.

Перехід скидає лічильники передавання й сповіщень про `DeadLetter` для поточного циклу. Перед скиданням Infrastructure у тому самому збереженні до бази даних записує аудит із попереднім станом, кількістю спроб, обмеженими діагностичними даними, причиною, ідентичністю ініціатора й часом запиту. PostgreSQL `xmin` не дає двом одночасним запитам двічі запланувати той самий кінцевий стан. За наявним рішенням для розробки endpoint тимчасово має `[AllowAnonymous]` і записує `anonymous-development`, коли немає автентифікованої ідентичності; перед відкриттям цієї операції в продукційному середовищі потрібно ввімкнути `PolicyNames.CanManageOrders`.

## Наявна SOAP-операція

Змінювати WSDL не потрібно. Згенерований клієнт надає:

```text
CreateSiteRequest(RequestData) -> RequestDataOut

RequestData:
  CounterpartyId: string
  Comment: string
  OrderId: string
  Date: DateTime
  Items[]: { ProductId: string, Quantity: string, Amount: decimal }

RequestDataOut:
  DocId: string
  Comment: string
```

`RequestData.OrderId` завжди отримує незмінний локальний `OrderNumber`, а не технічний GUID. Той самий номер повторно використовується під час наступних спроб, щоб менеджер міг знайти документ у 1C за відображуваним номером. `Item.Amount` відображається зі значення `amount` у рядку запиту — загальної суми для всієї кількості в рядку. `RequestDataOut.DocId`, що підтверджує створення документа, відповідає `Accepted` і зберігається як `OneCDocumentNumber`; відповідь, у якій `DocId` повідомляє, що документ не створено, відповідає `BusinessError`, навіть якщо це поле непорожнє. Порожній `DocId`, повернутий без помилки SOAP/транспорту, також відповідає `BusinessError`; очищений `Comment` з обмеженою довжиною використовується як діагностичні дані.

Майбутній машинозчитуваний документ OpenAPI явно визначає `Idempotency-Key` як обов'язковий параметр заголовка UUID, зокрема відповідь на успішне повторення запиту й `409 Conflict`.
