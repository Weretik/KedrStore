# T150 — Jobs: `SyncOneCOrdersJob` sends and checks 1C requests

**Depends on:** T040, T060, T080, T100, T145

- [x] Create `src/Sales/Sales.Infrastructure/Integrations/OneC/Jobs/SyncOneCOrdersJob.cs` and its orchestration service under `src/Sales/Sales.Infrastructure/Integrations/OneC/Services/`.
- [x] Register the job and its dependencies in `src/Sales/Sales.Infrastructure/DependencyInjection/SalesInfrastructureExtensions.cs` and `src/Bootstrapper/Host.Jobs/Host.Jobs/JobsHostServicesExtensions.cs`.
- [x] Add a `sync-one-c-orders` switch branch to `src/Bootstrapper/Host.Jobs/Host.Jobs/Program.cs`. It resolves `SyncOneCOrdersJob`, calls `RunAsync(cancellationToken)`, then exits using the existing one-run host pattern.
- [x] Safely claim due `Pending`, `TransportError`, and `RetryScheduled` records where `NextAttemptAtUtc <= now`, plus stale `Sent` attempts; process the configured batch and wait the configured delay between SOAP calls. Defaults are 20 records, five seconds, and a 15-minute stale-`Sent` delay. Stale recovery reuses the same `OrderNumber`, which OneC ignores when it already exists.
- [x] Remove only `OrderIdempotencyRecord` rows whose `ExpiresAtUtc` has passed. This cleanup never selects, changes, or deletes an order or its 1C synchronization record.
- [x] Use Europe/Kyiv explicitly. Outside the configured sending window, make no SOAP call and move `NextAttemptAtUtc` to the next allowed time; the default is 07:00–20:00.
- [x] Send each claimed order through `ISalesOneCWriteClient`, always using its persisted `OrderNumber` as the 1C request key.
- [x] Check the synchronous `CreateSiteRequest` result after each send: non-empty `RequestDataOut.DocId` transitions to `Accepted`; empty `DocId` transitions to `BusinessError` and stores only a sanitized, bounded `Comment`; a transport exception schedules retries `5m → 15m → 30m → 60m → 3h` and transitions to `DeadLetter` after the configured maximum (default 10 attempts).
- [x] Invoke the dead-letter notifier only after the state transition to `DeadLetter` is persisted. Do not send a second Telegram notification when a later job execution sees an already-dead-letter record.
- [x] Add job tests for accepted response, 1C business rejection, transport failure/backoff, out-of-window deferral, maximum-attempt dead letter, and duplicate/concurrent claim protection.
- [x] Log structured `OrderId`, `AttemptCount`, `Status`, and correlation context without credentials, headers, or raw request payloads.

## Checkpoint

`dotnet run --project src/Bootstrapper/Host.Jobs/Host.Jobs -- --job=sync-one-c-orders` performs one safe delivery pass. The same job both sends a request and determines its accepted/business/transport outcome from the current SOAP response.

## T155 extension

T155 refines the accepted-response rule: `DocId` is accepted only when it identifies a created 1C document. A response indicating that no document was created is `BusinessError`, even when `DocId` is non-empty.

## Scope note

The current SOAP contract has no separate read operation for checking a previously created 1C document by `OrderId` or `DocId`. Therefore no polling job is created. If 1C later adds that operation, create a new feature task for reconciliation rather than changing this delivery job implicitly.
