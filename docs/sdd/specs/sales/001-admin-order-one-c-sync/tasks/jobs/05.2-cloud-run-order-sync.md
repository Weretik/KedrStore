# T160 — Jobs: Cloud Run deployment

**Depends on:** T150

- [x] Inspect `src/Bootstrapper/Host.Jobs/Host.Jobs/Dockerfile` before deployment. Its `ENTRYPOINT ["dotnet", "Host.Jobs.dll"]` already accepts Cloud Run arguments, so no Dockerfile change is required for `--job=sync-one-c-orders` unless the image build stops including a referenced project.
- [x] Update `.github/workflows/deploy-cloudrun.yml` so deployment creates or updates a dedicated Cloud Run Job named `onec-orders-sync`.
- [x] Configure that job with the current `Host.Jobs` image, one task, parallelism `1`, `--args=--job=sync-one-c-orders`, and the required `ConnectionStrings__Default`, `OneCSoap__Endpoint`, `OneCSoap__Username`, and `OneCSoap__Password` secrets.
- [x] Set Cloud Run platform retries to `0`. Retry timing is owned by `OneCOrderSync` state and the scheduled next execution; platform retries must not create an uncontrolled immediate retry loop.
- [x] Give the job a timeout exceeding the configured batch duration and preserve the existing project/region settings from the workflow.
- [x] Verify that a workflow deployment updates the jobs image and arguments without executing the order-sync job automatically.

## Checkpoint

The deployment workflow maintains the dedicated Cloud Run Job without configuring a schedule. The operator configures recurring Cloud Scheduler invocation manually. The job remains safe if manually executed for diagnostics because local state, stable `OrderId`, and retry scheduling protect 1C from duplicate documents.

## Result

The workflow creates or updates `onec-orders-sync` only. It does not call `gcloud run jobs execute` for this job. The 10-minute task timeout covers the 20-item batch with five-second pacing; retry delays remain persisted application state and are not process waits.
