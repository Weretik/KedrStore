# T160 — задачі: розгортання Cloud Run

**Залежить від:** T150

- [x] Перед розгортанням перевірити `src/Bootstrapper/Host.Jobs/Host.Jobs/Dockerfile`. Його `ENTRYPOINT ["dotnet", "Host.Jobs.dll"]` уже приймає аргументи Cloud Run, тому зміна Dockerfile для `--job=sync-one-c-orders` не потрібна, якщо збірка образу не перестане включати проєкт-залежність.
- [x] Оновити `.github/workflows/deploy-cloudrun.yml`, щоб розгортання створювало або оновлювало окрему Cloud Run Job `onec-orders-sync`.
- [x] Налаштувати задачу на поточний образ `Host.Jobs`, одну task, паралельність `1`, `--args=--job=sync-one-c-orders` і потрібні секрети `ConnectionStrings__Default`, `OneCSoap__Endpoint`, `OneCSoap__Username` та `OneCSoap__Password`.
- [x] Установити кількість повторів платформи Cloud Run у `0`. Час повтору визначають стан `OneCOrderSync` і наступний запланований запуск; повтори платформи не повинні створювати некерований негайний цикл.
- [x] Установити timeout задачі більшим за налаштовану тривалість пакета й зберегти чинні параметри проєкту/регіону з workflow.
- [x] Перевірити, що workflow розгортання оновлює образ та аргументи задачі без автоматичного запуску синхронізації замовлень.

## Контрольна точка

Workflow розгортання підтримує окрему Cloud Run Job без налаштування розкладу. Оператор налаштовує регулярний виклик Cloud Scheduler вручну. Задача залишається безпечною для ручної діагностики, оскільки локальний стан, сталий `OrderId` і планування повторів захищають 1С від дублювання документів.

## Результат

Workflow лише створює або оновлює `onec-orders-sync`. Він не викликає для неї `gcloud run jobs execute`. Десятихвилинний timeout задачі покриває пакет із 20 елементів із п'ятисекундними інтервалами; затримки повторів залишаються збереженим станом застосунку, а не очікуванням процесу.
