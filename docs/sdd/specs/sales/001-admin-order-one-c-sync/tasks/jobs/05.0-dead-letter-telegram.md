# T145 - Jobs: Dead-letter Telegram notification and Excel export

**Depends on:** T010, T020, T040, T100

**Decision (2026-09-02):** use bounded durable retries on `OneCOrderSync`. A failed Telegram notification is retried by later `sync-one-c-orders` runs at `5m -> 15m -> 30m -> 1h -> 3h`, for at most five notification attempts. After the fifth failure, the notification is marked exhausted for observability; the persisted `DeadLetter` order state is unchanged and the 1C request is never resent.

- [x] Add `ProductName` to `OrderLine` as the immutable product-name snapshot received during manager order creation; map and persist it with the line so an export does not depend on the current catalog.
- [x] Define Sales Application contracts for a dead-letter notification and an order Excel export under `src/Sales/Sales.Application/Features/Orders/DeliveryFailure/`. The DTO includes order ID, counterparty name/ID, final sanitized error, and persisted order lines.
- [x] Implement `Sales.Infrastructure` adapters under `Notifications/` and `Exports/`: send an HTML Telegram message and attach an `.xlsx` file. Reuse the configured Telegram bot connection, but do not depend on Catalog's `CreateOrderRequest`, `ITelegramNotifier`, or `IOrderExcelExporter` contracts.
- [x] The Telegram caption contains: `DeadLetter` status, local order ID, current counterparty name and ID, final sanitized error, attempt count, and timestamp. Read client data from `Counterparty`; do not create customer snapshots in `Order`. The file contains all lines: product ID, product name, quantity, line amount, and order total.
- [x] Ensure notification failure is logged and scheduled for the bounded durable retry policy above without changing a successfully persisted `DeadLetter` state or re-sending the 1C request. Claim notification attempts with the existing PostgreSQL optimistic concurrency token.
- [x] Add tests for Excel content, caption sanitization, a single notification per dead-letter transition, and Telegram transport failure.

## Checkpoint

An undeliverable order is visible to operators in Telegram with sufficient context to act, while the persisted order and its terminal delivery status remain the source of truth.
