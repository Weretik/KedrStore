# Backend design

## Перевірений базис 2026-10-21

`AdminOrdersController` володіє `/api/admin/orders`; `OrderReadService` уже читає Orders із `Counterparties` та `OneCOrderSyncs`, але підтримує лише точний `counterpartyId` і порядок за датою. `CreateOrderCommandHandler` приймає `Amount` від клієнта; `OrderProductReader` повертає лише ID й ім’я. У Catalog є `ProductPrices`; у Sales Counterparty є `DefaultPriceTypeId` та правила категорій. Новий розрахунок потребує окремого читача цін, який бере політику **вибраного** клієнта за `counterpartyId`, а не політику поточного identity user.

## Рішення

- Власник — Sales; Catalog надає читання товару, категорії, актуальної ціни й доступності через контракт Application/Infrastructure. Не вводити прямої залежності Domain Sales від Catalog.
- Окремий Admin controller/handlers/DTO для `/api/admin/order-workspace`; існуючі операції залишаються сумісними. Нові DTO не містять клієнтського `amount`.
- Розрахунок і створення використовують одну серверну pricing policy, щоб не розійтися за правилами; на POST Order розрахунок повторюється. За зміни суми від показаної у попередньому розрахунку сервер повертає конфлікт із новою безпечною quote-проєкцією, щоб користувач підтвердив нову суму перед повтором. Контракт expected quote fingerprint визначити у версійному OpenAPI до коду.
- Для читання — `AsNoTracking`, проєкція у SQL, `Count` після умов і до пагінації, whitelist сортування, без завантаження позицій для списку. Уникати `ToLower` над колонками в умовах; для PostgreSQL перевірити `ILIKE`/індекси та план `EXPLAIN` на реальному обсязі перед вибором індексу. Виміряти окремо пошук і сортування за сумою.
- Створення використовує той самий атомарний механізм Order + sync + idempotency, але нову operation scope/key, щоб не змішати повтори двох контрактів. Чинний job не змінює чернетки.
- Для прав доступу застосувати `PolicyNames.CanManageOrders`; узгодити прив’язку ролей до політики перед rollout.
- Оновити коротку Sales feature-карту та індекс контрактів після реалізації. Міграція Orders не очікується; якщо ціна за одиницю потрібна у відповіді, її можна обчислити із збереженої суми рядка/кількості лише за перевіреної точності.

План задачі має зафіксувати тестові випадки для зміни ціни, відсутньої ціни, повтору ключа, багатослівного пошуку й фільтра клієнта. Повний прогін і запуск job поза обсягом документації.
