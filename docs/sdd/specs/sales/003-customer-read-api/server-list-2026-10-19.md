# Розширення списку клієнтів для серверної таблиці — 2026-10-19

**Спільний обсяг:** Admin DataGrid товарів і клієнтів. **Стан:** реалізовано в Sales API; докази початкової реалізації у [README](README.md) не підтверджують цю зміну.

## Мета і межі

Адміністратор шукає та фільтрує весь набір активних клієнтів Sales, а не лише вже завантажену сторінку. Залишаються чинними R-001–R-006, обсяг полів списку, анонімний доступ і маршрут `GET /api/admin/customers`. Деталі клієнта, зміна даних і модель зберігання не змінюються. Міграція БД не потрібна.

## Правила

- **R-007:** `searchTerm` шукає без урахування регістру підрядок у `counterpartyId`, `name` або `phone`; порожній/пробільний рядок означає відсутність пошуку.
- **R-008:** Необов'язкові `counterpartyId`, `name`, `phone` фільтрують відповідні поля за підрядком без урахування регістру. Одночасні фільтри й `searchTerm` поєднуються через AND. Порожній фільтр не обмежує результат.
- **R-009:** `sort` має значення `name`, `-name`, `counterpartyId`, `-counterpartyId`, `phone`, `-phone`; типово `name`. Напрямок застосовується до вибраного поля, `counterpartyId` є стабільним другим ключем, коли перший ключ не є ID. Непідтримуваний `sort` дає `400`.
- **R-010:** Усі фільтри та пошук застосовуються до активних клієнтів **до** `totalRecords`, `totalPages`, `Skip` і `Take`. Метадані відповідають відфільтрованому набору; сторінка за межами набору повертає порожній `value` і коректний `totalRecords`. Зберігаються `page >= 1`, `1 <= pageSize <= 100`, типові `1/20`.

## HTTP-контракт

`GET /api/admin/customers`, `operationId: getAdminCustomers`. Додаткові необов'язкові query-параметри: `searchTerm`, `counterpartyId`, `name`, `phone`, `sort`. Тип усіх — string; для непорожнього тексту обрізаються крайні пробіли. Поля відповіді та коди помилок залишаються як у [контракті](contracts/api-contract.md); канонічну схему оновити в `docs/sdd/contracts/sales/customer-read.openapi.yaml` перед transport/client. Існуючий виклик лише з `page/pageSize` продовжує працювати.

## Сценарії приймання

- **SC-005:** Є збіги на першій і наступних сторінках, а також логічно видалений клієнт. Пошук за частиною ID/імені/телефону повертає всі активні збіги у стабільному порядку; `totalRecords` рахує всі збіги до пагінації.
- **SC-006:** Фільтри `name` і `phone` разом із `searchTerm` звужують **увесь** активний набір через AND; нуль збігів повертає `value: []` і `totalRecords: 0`.
- **SC-007:** Кожне підтримуване сортування застосовується перед пагінацією; повторний запит сторінки дає сталий склад рядків. Невідомий ключ сортування повертає `400`.

## Дизайн і план

Розширити HTTP request, Application query/validator та `CustomerReadService` без завантаження всіх рядків у пам'ять. Предикати, порядок, count і page виконуються в SQL через чинний EF Core контекст. Зберегти проєкцію лише трьох полів і виключення `IsDeleted`. Індексування додавати лише за окремо доведеної потреби.

1. **EN-004:** зафіксувати наведені параметри у версійному OpenAPI та перевірити сумісність з наявним контрактом.
2. **TS-007:** провести query-параметри через API/Application, валідувати sort і межі текстових полів.
3. **TS-008:** реалізувати серверні предикати й стабільне сортування до count/page.
4. **TS-009:** цільові тести SC-005–SC-007 на рівні Sales persistence/API; виконати лише потрібні тести цієї фічі, звірити контракт і код. Повний прогін проєкту та браузер — лише за окремим запитом користувача.
