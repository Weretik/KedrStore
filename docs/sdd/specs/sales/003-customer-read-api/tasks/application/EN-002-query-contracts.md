# EN-002 — Визначити контракти запитів клієнтів

- **ID завдання:** EN-002
- **Забезпечує:** SC-001, SC-002, SC-003
- **Залежить від:** EN-001
- **Точні шляхи:** `src/Sales/Sales.Application/Contracts/Customers/ICustomerReadService.cs`, `src/Sales/Sales.Application/Features/Customers/GetList/DTOs/`, `src/Sales/Sales.Application/Features/Customers/GetById/DTOs/`
- **Рівень тестування:** перевірка компіляції Application і контрактів

## Чому це спільна передумова

Обробники списку й деталей використовують спільну абстракцію читання з обмеженим набором приватних даних. Якщо визначити її першою, Application не залежатиме від EF і сховища Identity.

## Робота

- [x] Визначити одну абстракцію читання Application для проєкцій списку й деталей активних клієнтів.
- [x] Визначати записи для рядка списку, деталей, правил цін, посторінкового виводу й фільтрів лише тоді, коли цього вимагає EN-001.
- [x] Виключити доменні сутності, типи EF, поля видалення й аудиту, `IdentityUserId` та персональні дані, якщо їх явно не погоджено.
- [x] Залишити читання замовлень у фічі 002, не пов'язуючи графи замовлень із проєкціями клієнтів.
- [x] Передавати `CancellationToken` через кожну операцію читання.

## Виняток із підходу «спочатку тест» і замінна перевірка

- **Причина:** контракти часу компіляції передують тестам поведінки обробників та інфраструктури.
- **Замінна перевірка:** зібрати `src/Sales/Sales.Application/Sales.Application.csproj` і скомпілювати цільові тестові фікстури.
- **Результат:** `dotnet build src/Sales/Sales.Application/Sales.Application.csproj --no-restore` пройшов; цільові фікстури скомпільовано, згодом їхні тести пройшли.

## Контрольна точка

Сценарії використання списку й деталей мають сталі, мінімальні контракти Application, що відповідають рішенню щодо приватності.
