# Назви довідників у деталях клієнта — 2026-10-19

**Стан:** реалізовано; цільову перевірку виконано 2026-10-19. **Модулі:** Sales читає наявні довідники Catalog через його application-контракт. **Обсяг:** `GET /api/admin/customers/{counterpartyId}`, `operationId: getAdminCustomerById`.

## Мета й перевірені джерела

Картка клієнта повинна показувати назву типового типу ціни та назву типу ціни для кожного правила категорії. Категорію слід показувати за назвою разом з її ID. Чинна Sales-відповідь має лише `defaultPriceTypeId` та пари `categoryId`/`priceTypeId`. Назви зберігаються у Catalog: `PriceType.PriceTypeName` і `ProductCategory.Name`. Нових таблиць або міграції не потрібно.

## Правила

- **R-011:** Відповідь зберігає наявні ID для сумісності й додає `defaultPriceTypeName: string | null` та в кожне `categoryPriceTypes[]` — `categoryName: string | null`, `priceTypeName: string | null`. Назви беруться за відповідними ID з Catalog під час читання; ID і назви одного запису не можуть змішуватися з іншими.
- **R-012:** Відсутній у Catalog довідниковий запис не приховує клієнта чи правило: відповідна назва дорівнює `null`, ID лишається. UI позначає таку назву як недоступну; тип ціни не замінює його числовим ID як основним підписом.
- **R-013:** Читання виключає логічно видаленого клієнта згідно з R-002, не викликає 1C і не змінює дані Sales/Catalog. Пошук назв виконується пакетно за наборами ID, без запиту на кожне правило. Порядок правил за `categoryId` зберігається.

## Приймальні сценарії

- **SC-008:** Для клієнта з типовим типом ціни 1 та правилом `categoryId=5513`, `priceTypeId=7` Catalog містить обидва типи цін і категорію. Відповідь має узгоджені `defaultPriceTypeName`, `categoryName`, `priceTypeName` та всі три ID; правило лишається на місці.
- **SC-009:** Якщо тип ціни або категорія відсутні в Catalog, відповідне поле назви є `null`; відповідь `200`, ID і інші правила збережено.
- **SC-010:** Невідомий або логічно видалений клієнт повертає поточний `404` без запитів довідників; 1C і зміни стану відсутні.

## Контракт, дизайн та задачі

Зміна лише адитивна: нові nullable-поля в `CustomerDetail` і `CustomerCategoryPriceType` канонічного `docs/sdd/contracts/sales/customer-read.openapi.yaml`; список клієнтів не змінюється. Sales Application DTO містить назви, а Sales Infrastructure після пошуку клієнта отримує один набір назв категорій і один набір назв типів цін через `ICatalogReferenceDataReader` (контракт Catalog.Application), із наявного Catalog DbContext. Невідомі ID повертають `null`. Нова модель доступу чи HTTP-помилка не додається.

| Задача | Сценарії | Залежність | Цільовий доказ |
| --- | --- | --- | --- |
| EN-005 — OpenAPI та lookup-контракт Catalog | SC-008–SC-010 | немає | поля, nullable-семантика, пакетний інтерфейс |
| TS-010 — проєкція Sales і транспорт | SC-008–SC-010 | EN-005 | іменовані значення без N+1 та збережений `404` |
| TS-011 — тести й документація фічі | SC-008–SC-010 | TS-010 | цільові тести деталей і відсутніх довідників; оновлена карта клієнтів |

Перевіряти тільки змінену фічу автоматичними тестами; повний прогін і браузер — лише за окремим проханням користувача. Невирішених продуктових рішень немає.
