Инструкция по синхронизации SALES -> 1C (Cloud Run, повторы, расписание)

Контекст:
- Сервис работает в Google Cloud Run и может "засыпать" (scale to zero).
- Заказы должны надежно доходить до 1С.
- Нужно понимать, приняла ли 1С заявку.
- Если не приняла или был транспортный сбой, нужны повторы с интервалом (без спама).
- Нужно ограничение по времени отправки (например, 09:00-18:00 Europe/Kyiv).

Базовый подход (безопасный для продакшена):
1) Использовать транзакционное сохранение в БД Sales:
   - сохранить Order;
   - сохранить запись синхронизации OneCOrderSync со статусом Pending;
   - закоммитить в одной транзакции.

2) Не зависеть от немедленной отправки "из памяти" во время HTTP-запроса.
   - Отправка в 1С должна идти из фонового процесса по расписанию.

3) Запускать периодически:
   - Cloud Scheduler -> Cloud Run Job (или защищенный endpoint сервиса Cloud Run);
   - запуск каждые N минут.

4) Вести состояние синхронизации каждого заказа в таблице БД:
   Минимальные поля:
   - Id
   - OrderId
   - Status:
     Pending, Sent, Accepted, BusinessError, TransportError, RetryScheduled, DeadLetter
   - AttemptCount
   - NextAttemptAtUtc
   - LastAttemptAtUtc
   - LastHttpStatus
   - LastErrorCode
   - LastErrorMessage
   - OneCRequestPayloadHash (без чувствительных данных)
   - OneCResponseBody (санитизированный/обрезанный)
   - AcceptedAtUtc

5) Логика повторов:
   - Если 1С недоступна / timeout / ошибка сети или шлюза:
     ставим TransportError и планируем повтор.
   - Если 1С ответила "принято":
     ставим Accepted и больше не повторяем.
   - Если 1С вернула внутреннюю бизнес-ошибку:
     ставим BusinessError (обычно без агрессивных авто-повторов, по правилу бизнеса).
   - Использовать контролируемый backoff, например:
     5м -> 15м -> 30м -> 60м -> далее раз в 3ч.
   - Ограничить максимум попыток; при превышении -> DeadLetter + ручная обработка.

6) Защита от спама в 1С:
   - Обрабатывать небольшие батчи за один запуск (например 20-50 записей).
   - Делать rate limit или короткую паузу между отправками (например 1-3 сек).
   - Брать только записи, где NextAttemptAtUtc <= now.

7) Ограничение по времени отправки (пример 09:00-18:00 Europe/Kyiv):
   - Если сейчас вне окна: не отправлять, переносить NextAttemptAtUtc на ближайшее разрешенное время.
   - Часовой пояс должен быть задан явно и детерминированно.
   - Cron в Scheduler тоже настроить в этом окне.

8) Идемпотентность (критично):
   - В 1С отправлять стабильный внешний ключ (ExternalOrderId = OrderId).
   - При повторе отправлять тот же ключ.
   - Это защищает от дублей документов/заказов в 1С.

9) Наблюдаемость:
   - Структурные логи с полями: OrderId, AttemptCount, Status, CorrelationId.
   - Метрики:
     количество accepted, транспортные ошибки, бизнес-ошибки, размер очереди retry, размер dead-letter.
   - Алертить, если растет dead-letter или падает доля успешных accepted.

10) Практический CQRS-поток в Sales:
   - CreateOrderCommand:
     сохраняет Order + OneCOrderSync(Pending), затем commit.
   - Плановый SyncOneCOrdersJob:
     берет due-записи, отправляет в 1С, обновляет статус, планирует повторы.

11) Безопасность данных:
   - Не хранить секреты/токены/сырые чувствительные payload в логах и таблице.
   - Хранить только нужные для диагностики данные ответа.

Итог:
- "Сон" Cloud Run не проблема.
- Надежность достигается за счет состояния в БД + плановых повторов.
- 1С защищена от резкого спама.
- По каждому заказу всегда виден текущий статус доставки в 1С.
